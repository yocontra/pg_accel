# H3 overflow spool lifecycle checkpoint

Status: design only, 2026-10-25. No implementation, build, server activity or publication. Native repair still requires user approval and implementation review.

## Evidence and limits

Actual local source trees were found at `.pgaccel/postgres/src/postgresql-18.4/` and `.pgaccel/postgres/src/postgresql-19beta1/`. The five files below in each tree were byte-compared with matching upstream REL_18_4 / REL_19_BETA1 sources; all ten matched. This confirms inspected source, not source-to-installed-binary provenance. Earlier scoped scratch search found only headers; the later broader search resolved that limitation. PG17 source was not used as authority and was not modified.

Paths below are relative to each tree's `src/backend/`; line pairs are PG18 / PG19:

- `utils/sort/tuplestore.c`: begin captures CurrentResourceOwner and creates a child generation context (276–279 / 277–280); spill temporarily selects that owner and the parent allocation context (852–867 / 853–868). End calls BufFileClose before deleting contexts/state (492–500 / 493–501).
- `storage/file/buffile.c`: allocations belong to creation context and external resources to creation owner (26–29 both); BufFileClose FLUSHES before closing files (412–421 / 413–422). Therefore end is fallible, including during error cleanup.
- `storage/file/fd.c`: OpenTemporaryFile(false) registers the VFD and marks delete-at-close and temp-file-limit accounting (1728–1775 / 1712–1759). Limit failure raises configuration-limit SQLSTATE (2286–2290 / 2270–2274). Resource cleanup calls FileClose directly, not BufFileFlush (4104–4114 / 4089–4099), with AFTER_LOCKS registration (364–370 / 365–371).
- `utils/mmgr/mcxt.c`: reset/delete processes children before parent callbacks (389–418,460 onward / 406–435,475 onward).
- `utils/resowner/resowner.c`: recursive ResourceOwnerRelease and AFTER_LOCKS release exist (658,794 / 655,791). Use PostgreSQL's existing owner; do not globally release unrelated resources or introduce inter-transaction files.

Upstream primary references: [PG18 tuplestore](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/utils/sort/tuplestore.c), [PG19 tuplestore](https://raw.githubusercontent.com/postgres/postgres/REL_19_BETA1/src/backend/utils/sort/tuplestore.c), [PG18 BufFile](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/storage/file/buffile.c), [PG19 BufFile](https://raw.githubusercontent.com/postgres/postgres/REL_19_BETA1/src/backend/storage/file/buffile.c), [PG18 fd](https://raw.githubusercontent.com/postgres/postgres/REL_18_4/src/backend/storage/file/fd.c), [PG19 fd](https://raw.githubusercontent.com/postgres/postgres/REL_19_BETA1/src/backend/storage/file/fd.c).

Existing extension conventions: `pg_accel/src/engine/ffi/custom_scan/mod.rs:306–379` provides exactly-once installed-owner release and query-context callback; `:966–1011` catches PostgreSQL errors before query-context deletion and rethrows original error. Aggregate installation currently supplies no reset preparation callback (`:911`); raster has one. `executor/raster.rs:620–648` invalidates already-deleted child pointers before Drop. `executor/agg/execute.rs:265` owns rescan reset, and `:290` owns tuple fetching.

Exact required ownership expansion: `pg_accel/src/engine/ffi/custom_scan/mod.rs` and `tests.rs`, together with planned `executor/agg/execute.rs` and `output.rs`. The caught-error helper currently drops directly and DOES NOT invoke the query-reset preparation hook. Add a distinct typed aggregate abort-detach hook there (and a separate aggregate query-reset hook); both make handles inert without PostgreSQL calls. Wire the hooks into the installed ownership record before preparation. Add an explicit fallible normal-close call before normal release/reset. Spool Drop itself must be strictly non-PostgreSQL and non-flushing, so even an unexpected drop cannot enter a second PG error. Do not reuse raster's live-context Drop behavior for a spool.

## Concrete proposed lifecycle

1. Keep the one-shot path unchanged. On typed overflow, transition an already-installed AggExecState to BuildingSpool. Create a dedicated child of es_query_cxt, not a per-tuple context. Begin a forward-readable heap tuplestore with `interXact=false` and current `work_mem`. Retain the ambient query/portal resource owner captured at creation; no SPI/internal subtransaction or owner switching by extension code around this operation. Record context ownership before the first allocating call; assign the returned store pointer immediately, before any later fallible operation. Creation failure leaves PostgreSQL-owned allocations to context/owner teardown.
2. Keep partition control, converted-mask owner, current native output batch and all execution charges in the installed executor, not solely on a Rust stack crossing error-capable PG calls. Drop STORE leases and native borrowed pointers before spool writes/materialization/interrupt delivery. Copy each final tuple into the tuplestore, then clear/reset the bounded staging slot/context. Release each native batch before allocating the next; no host result accumulation.
3. Preserve/restore CurrentMemoryContext around every operation that switches it, on success and caught error, using the project's pgrx-aware catch/finally conventions. Do not rely on a plain Rust Drop guard to survive PostgreSQL longjmp. Existing PG routines can also temporarily switch CurrentResourceOwner while spilling; the error boundary must restore the entry owner before rethrow. Never restore a pointer after its context/owner has already been destroyed.
4. Complete every partition before switching BuildingSpool to ReadySpool and returning a tuple. Maintain explicit Exhausted state; EOF must not mean Unprepared or trigger redispatch. Reads use a slot with independent copied tuple ownership so later spool/context teardown cannot leave dangling slot data. A final write/read transition can flush and fail; do not mark the query successful based solely on completion of native leaves. Subsequent disk-read errors remain ordinary PostgreSQL errors, never partial successful completion.
5. Normal EOF/end/rescan uses an explicit fallible close method while the executor remains installed. Move/take the spool handle into a Closing state BEFORE calling tuplestore_end, so a catch cannot retry a partially closed pointer. Do not clear the entire executor ownership record before this call. On success clear slots, delete the dedicated parent context, and mark Closed. On failure detach the handle, release Rust/native owners without PostgreSQL flushing, and rethrow the original SQLSTATE/message. EndCustomScan and ReScanCustomScan need an error boundary covering this explicit close; their current generic drop/reset is insufficient for a fallible spool close. Rescan then discards all results/partition state and rebuilds from current inputs rather than rewinding stale results.
6. ERROR/cancellation catch must NOT invoke tuplestore_end or BufFileClose, directly or from Rust Drop: their flush could fail again and replace the original error or cause double unwind. Mark spool abandoned, clear raw handles without dereference, and release Rust/native/ledger owners exactly once. Rethrow the original error. PostgreSQL closes/deletes non-interXact VFDs through its captured resource owner during normal error/transaction/portal cleanup; query context teardown frees spool memory. This is deferred PostgreSQL cleanup, not a claim that the catch instantly closes every file.
7. Query-context-reset-only backstop likewise invalidates all child-context/slot/store pointers before dropping the Rust executor. It must never touch freed memory or perform file flush. The associated owner teardown closes VFDs. Normal end/rescan must explicitly close instead of relying on this backstop. Do not register an end-calling callback on the spool context: its own generation child may already be deleted when that callback runs.

Work_mem is PostgreSQL's approximate tuplestore threshold, not a hard total-RSS cap: allow bounded current tuple, pointer arrays, allocator/BufFile overhead and one native output batch. State the bound honestly and test spill; do not claim exact work_mem-byte peak. No independent temp-file implementation or private inspection of opaque Tuplestorestate is needed.

## Required acceptance tests before this checkpoint becomes implementation proof

Both production majors: force overflow with small capacity and low work_mem; prove disk storage via tuplestore stats/in-memory probe and full multiset parity; test NULL/zero-count groups plus ORDER/LIMIT and repeated EOF without dispatch. Check current native-batch and mask charges at every boundary.

Existing `custom_scan/tests.rs` cleanup instrumentation must cover normal EOF/end and early portal close, completed-spool rescan and BuildingSpool rescan/reset, query-context callback after normal close, callback-only abort, caught error while building and while reading, and exactly-once release. Add aggregate reset-preparation coverage analogous to raster.

Inject failure after owner install, after context creation, after store creation, after a completed leaf, during a write/read, and at explicit close. Use real low temp_file_limit spill failure and cancellation during partition work; verify the original SQLSTATE/message survives and no rows escape before all leaves complete. A close-flush error must not call end twice. Verify ledger return to baseline, no live native output owners, and backend-specific temporary-file disappearance after subtransaction/transaction or portal resource cleanup. Test a subsequent successful query in the same backend, not merely process exit. No changes to global temp directories or other backends.

Use prepared valid→noncanonical→valid mutation and rollback, with rescan/reload, to establish fresh generation binding and no stale transport reuse. Unit tests separately exercise Building/Ready/Exhausted/Closing/Abandoned transitions, failed creation/close, and reset pointer invalidation without dereferencing freed context memory.

Conclusion: PostgreSQL provides the necessary storage and owner cleanup. The mandatory design correction is split fallible normal-close versus non-flushing abort cleanup, with installed ownership retained across PG calls. The checkpoint is resolved as a feasible design; safety remains contingent on implementation and the tests above, not certified by source inspection alone.
